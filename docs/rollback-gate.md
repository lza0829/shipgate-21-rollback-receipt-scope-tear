# 回退时段写闸 —— 架构口径（全局唯一）

## 选定的一臂
**臂一：以回退时段真正卡写为准（硬闸 hard-gate）。**

- 回退时段（rollback_windows，按环境取最新一条）为「窗关」或不存在开放记录时，
  回退写口 **整笔失败**：发版单不得进入「已回滚」、名册 `app_env_versions` 不变、
  实例 `instances` 版本不变、对账不得提前计成功。
- 拒绝仍留下**可核痕迹**：独立事务写一条 `audit_events(kind='回退拒因')`，
  并在 `/对账` 的「时段外回退」桶中计数。绝不只把前端按钮置灰。
- 另一臂（时段关闭仅提示仍可写、打时段外标记）**不采用**，代码中不存在第二套口径。

## 共用一个成败（六处同命运）
回退写口在单个 SQLite 事务（`BEGIN IMMEDIATE` 写事务）内顺序完成：
1. 打写锁并复查发版单状态（条件 UPDATE，防双回退写出两个目标版本）；
2. 读侧/写侧共用同一判定函数 `rollback_window_open(conn, env_id)`
   —— 读侧 `/回滚窗` 的 `可回退` 字段与写侧卡闸用的是同一份谓词，不各判各的；
3. 闸不过 → 抛错，事务回滚（业务数据零改动），拒绝痕迹由独立事务落库；
4. 闸过 → 发版单置「已回滚」、名册目标旧版、实例整组收口到目标旧版，一次 commit。
任一步失败整体 rollback，回到操作前，杜绝「名册已旧、实例仍新」的半截分叉。

## 并发（两人同时回退）
- 写事务一律 `BEGIN IMMEDIATE` 立即拿库级写锁 + `busy_timeout`，第二个写者等待；
- 状态迁移用条件 `UPDATE ... WHERE status IN ('已放行','晋升中')` 并校验 rowcount，
  先提交者把状态改成「已回滚」，后提交者条件落空 → 整笔失败，只会有一个目标版本。

## 对账分桶（硬闸口径，只有一种）
`/对账` 新增「时段外回退」桶：
- `时段外回退尝试`：kind='回退拒因' 的审计条数（被硬闸拦下的请求）；
- `时段外成功回退`：恒为 0（硬闸下不可能出现，显式列出自证口径）；
- `窗口内成功回退`：kind='回滚' 且其发版单回退时窗口开放的成功回退数。
被拒请求不计入「已回滚」成功统计。

## 审计范围过滤
`/审计` 支持 `类别`、`动作关键字`、`关联编号` 查询参数（默认全部），
回退相关审计 kind 为「回滚」（成功）与「回退拒因」（时段外硬拒）。

## 边界
本闸只管「回退时段写范围」。金丝雀比例真源仍为 releases.canary_ratio /
settings.金丝雀默认比例，另立，不在本闸内改动。
